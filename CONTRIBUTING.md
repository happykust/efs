# Участие в разработке

Спасибо за интерес к efc. Здесь описано, как собрать проект, что проверяется в CI и как оформлять изменения.

## Быстрый старт

```bash
git clone https://github.com/happykust/efc.git
cd efc
uv sync
uv run efc --help
```

`uv sync` ставит и рантайм-зависимости, и dev-группу (pytest, ruff). Отдельного шага установки для разработки не нужно.

## Проверки перед отправкой изменений

```bash
uv run pytest            # тесты
uv run ruff check .      # линтер
uv run ruff format .     # форматирование
```

Ровно эти три команды выполняет CI на Python 3.12, 3.13 и 3.14. Если они проходят локально, сборка на GitHub тоже пройдёт.

## Тесты

Тесты лежат в `tests/`, фикстуры и конструкторы минимальных SBOM — в `tests/conftest.py`.

Правило без исключений: **тесты не ходят в сеть и не запускают внешние процессы**. HTTP мокается через `responses`, вызовы `subprocess` и функции проверки репозиториев — через `monkeypatch`. Тест, которому нужен реальный `git`, `cdxgen` или доступ к API, написан неправильно.

Для нового кода тест обязателен. Для исправления бага — сначала тест, воспроизводящий ошибку.

## Стиль кода

- Python 3.12+, длина строки 120, форматирование ruff.
- Документация, комментарии, сообщения об ошибках и вывод CLI — на русском языке.
- SPDX-заголовки обязательны в каждом файле:

```python
# SPDX-FileCopyrightText: 2026 Ваше Имя
# SPDX-License-Identifier: Apache-2.0
```

Файлы, унаследованные от исходного проекта sbom-checker, сохраняют строку копирайта ИСП РАН — не удаляйте её, добавляйте свою следом.

- Комментарии объясняют «почему», а не «что». Комментарий, пересказывающий соседнюю строку кода, не нужен.

## Структура проекта

CLI построен на typer: `efc/cli.py` — единственная точка входа, она разбирает аргументы и передаёт их в `run(args)` соответствующего модуля. Логика команд живёт в модулях (`checker.py`, `updater.py`, `postprocess.py`, ...), в CLI её быть не должно.

## Коммиты и pull request'ы

- Заголовок коммита — одной строкой, на английском, в формате Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `ci:`, `build:`, `style:`.
- Ломающие изменения помечаются восклицательным знаком: `refactor!: ...`.
- Одно изменение — один коммит. Форматирование не смешивается с содержательными правками.
- Изменения, заметные пользователю, добавляются в `CHANGELOG.md` в раздел `Unreleased`.

## Релизы

Версия задаётся в `pyproject.toml`. Релиз выпускается тегом:

```bash
git tag v1.1.0
git push origin v1.1.0
```

Дальше всё делает workflow `release.yml`: собирает дистрибутивы, публикует их в PyPI через trusted publishing и создаёт релиз на GitHub. Токены PyPI в секретах репозитория не хранятся.
