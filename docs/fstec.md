# Подготовка перечня под ФСТЭК

Руководство ведёт от исходников продукта до готового перечня заимствованных программных компонентов, пригодного для сдачи. Каждый шаг объясняет, что именно требуется и почему.

## Что должно получиться

Перечень заимствованных компонентов — документ, описывающий все сторонние компоненты в составе продукта. Для каждого компонента нужно знать: название, версию, язык исходного кода, где взять исходный код и относится ли компонент к поверхности атаки или к функциям безопасности.

efs хранит перечень в формате CycloneDX 1.6 (JSON) с расширениями ГОСТ и выгружает его в CSV или ODT для приложения к комплекту документов.

## ГОСТ-свойства

Свойства записываются в массив `properties` каждого компонента. Все четыре — обязательные к заполнению, если применимы.

### GOST:attack_surface

Принадлежность компонента к поверхности атаки программного обеспечения.

| Значение | Когда |
|----------|-------|
| `yes` | Компонент обрабатывает данные, поступающие извне доверенной границы |
| `indirect` | Компонент не принимает внешние данные сам, но используется теми, кто принимает |
| `no` | Компонент не участвует в обработке внешних данных |

Значение определяет разработчик, исходя из архитектуры продукта — автоматически его вывести нельзя. По умолчанию efs проставляет `no`; менять его на `yes` для конкретных компонентов нужно осознанно, через конфиг.

### GOST:security_function

Принадлежность к компонентам, реализующим функции безопасности: криптография, аутентификация, разграничение доступа, контроль целостности, регистрация событий безопасности.

Значения те же: `yes`, `indirect`, `no`. Тоже заполняется вручную — библиотеку вроде `cryptography` или `pyjwt` инструмент не отличит от прочих без знания того, как она используется.

### GOST:source_langs

Язык исходного кода компонента. **Если компонент написан на нескольких языках, каждый язык указывается отдельным свойством** — не списком через запятую:

```json
"properties": [
  {"name": "GOST:source_langs", "value": "Python"},
  {"name": "GOST:source_langs", "value": "C"}
]
```

Это единственное ГОСТ-свойство, которое efs заполняет сам: язык однозначно следует из экосистемы пакета (`pkg:pypi` → Python, `pkg:npm` → JavaScript и так далее). Исключение — `pkg:deb` и `pkg:rpm`: в дистрибутивных пакетах язык произвольный, и угадывать его в документе для регулятора нельзя. Подробности — в [описании конфига](config.md#языки-программирования).

### GOST:provided_by

Название сертифицированного средства защиты информации, в составе которого поставляется компонент.

Свойство закрывает случай, когда исходный код компонента недоступен, потому что компонент получен в составе сертифицированного СЗИ. Для такого компонента ссылка на репозиторий не требуется — вместо неё указывается СЗИ.

Практическое следствие: у каждого компонента должно быть либо `externalReferences` типа `vcs` со ссылкой на исходный код, либо `GOST:provided_by`. `efs check` проверяет именно это условие.

## Шаг 1. Сгенерировать SBOM

efs не сканирует код сам, а запускает внешний сканер — cdxgen или trivy.

```bash
efs init          # интерактивный мастер: выберет инструмент и настроит конфиг
efs scan          # или сразу, если конфиг уже есть
```

Что выбрать:

| Сканер | Сильные стороны |
|--------|-----------------|
| cdxgen | Богатые метаданные, много экосистем, точные графы зависимостей исходников |
| trivy | Быстро, хорошо разбирает контейнерные образы и ОС-пакеты, находит уязвимости |

Настройки сканера живут в секции `scanner` конфига — см. [справочник](commands.md#efs-scan).

Сканирование нескольких сервисов сразу: соберите SBOM по каждому и объедините через `efs merge`. Для сырых отчётов trivy объединение работает без предварительной обработки — см. [режим trivy](commands.md#режим-сырых-отчётов-trivy).

## Шаг 2. Создать конфиг

```bash
efs config init bom.json
```

Команда собирает из SBOM все purl и записывает их в `.efs-config.json`, сразу подставляя язык программирования там, где он выводится из экосистемы. Конфиг — то место, где вы один раз описываете решения по компонентам; при следующем обновлении SBOM они не потеряются.

Повторный запуск сохраняет уже сделанные настройки: добавляет новые компоненты и убирает исчезнувшие.

## Шаг 3. Заполнить то, что не выводится автоматически

Откройте `.efs-config.json` и пройдитесь по компонентам. Обычно нужно:

1. **Отметить поверхность атаки и функции безопасности** там, где они есть:

```json
"components": {
  "pkg:pypi/django": { "attack_surface": "yes" },
  "pkg:pypi/cryptography": { "security_function": "yes", "source_langs": ["Python", "C"] }
}
```

2. **Исключить то, что не входит в поставку** — тестовые и сборочные зависимости:

```json
"pkg:pypi/pytest": { "exclude": true },
"pkg:npm/eslint": { "exclude": true }
```

`exclude: true` убирает компонент вместе с его зависимостями, которые больше никому не нужны. Если зависимости должны остаться — `exclude: "direct"`. См. [каскадное исключение](config.md#как-работает-каскад).

3. **Описать форки** — если вы модифицировали заимствованный компонент, это документируется через `pedigree`:

```json
"pkg:pypi/cryptography": {
  "vcs": "https://github.com/our-org/cryptography-fork",
  "pedigree": {
    "ancestors": [{
      "type": "library", "name": "cryptography", "version": "42.0.0",
      "externalReferences": [{"type": "vcs", "url": "https://github.com/pyca/cryptography"}]
    }],
    "notes": "Патчи для совместимости с ГОСТ-криптографией"
  }
}
```

4. **Указать СЗИ** для компонентов без публичных исходников:

```json
"pkg:generic/crypto-module": { "provided_by": "КриптоПро CSP" }
```

Посмотреть, что осталось незаполненным, можно в любой момент:

```bash
efs config status
```

## Шаг 4. Найти ссылки на исходный код

Компонентам нужен адрес репозитория. Часть ссылок сканер проставляет сам, остальные efs ищет по внешним реестрам:

```bash
efs config find-vcs      # заполнит vcs в конфиге для компонентов без ссылки
```

Команда обращается к ecosyste.ms, PyPI, npm, Maven Central, Debian Sources и другим источникам, проверяет найденный адрес на то, что это действительно репозиторий, и записывает результат в конфиг. Результаты кешируются в `~/.cache/efs`, поэтому повторный запуск быстрый.

Ссылки, которые найти не удалось, останутся пустыми — их придётся указать вручную или отметить `provided_by`.

## Шаг 5. Собрать перечень

```bash
efs postprocess bom.json result.json \
  --app-name "МойПродукт" --app-version "1.0.0" --manufacturer "ООО МояКомпания"
```

На этом шаге efs убирает из SBOM лишние поля сканера, применяет всё, что описано в конфиге, проставляет ГОСТ-свойства и удаляет исключённые компоненты. Конфиг подхватывается из текущей директории автоматически.

## Шаг 6. Проверить готовность

```bash
efs check result.json
```

Проверка идёт в два слоя. Сначала файл валидируется по JSON Schema (CycloneDX 1.6 с ГОСТ-ограничениями), затем проверяется заполненность — то, чего схема не требует, но требует регулятор.

Результат виден по коду возврата, отдельного флага не нужно:

| Код | Значение |
|-----|----------|
| `0` | Перечень готов |
| `1` | Ошибки схемы или недоступные ссылки при `--check-vcs` |
| `2` | Ошибка вызова: неверный аргумент или отсутствующий файл |
| `3` | Схема в порядке, но перечень не заполнен |

В конце печатается сводка по видам замечаний:

```
не заполнено для сдачи:
  отсутствует GOST:source_langs: 1367
  нет ссылки на репозиторий и не указан GOST:provided_by: 2
файл соответствует схеме, но перечень не готов к сдаче: замечаний 1369
```

### Разбор типичных замечаний

| Замечание | Что делать |
|-----------|------------|
| `metadata.component.name не заполнено` | Передайте `--app-name` в `postprocess` или задайте `metadata.name` в конфиге |
| `отсутствует GOST:attack_surface` | Компонента нет в конфиге и не задан `defaults` — добавьте `defaults.attack_surface` |
| `отсутствует GOST:source_langs` | Язык не выводится из purl (обычно `deb`/`rpm`) — укажите его в конфиге или в `defaults.source_langs` |
| `нет ссылки на репозиторий и не указан GOST:provided_by` | Запустите `efs config find-vcs`, а для компонентов из состава СЗИ укажите `provided_by` |

Дополнительно можно проверить, что ссылки действительно рабочие:

```bash
efs check result.json --check-vcs --check-source-distribution
```

Проверка обращается к сети: `git ls-remote`, `svn ls`, `hg identify`, а для архивов — HTTP-запросы. На больших перечнях это занимает время, но результаты кешируются.

## Шаг 7. Выгрузить документ

```bash
efs export odt result.json perechen.odt      # ODT для приложения к документам
efs export csv result.json perechen.csv      # CSV для обработки
```

Для перечня образов контейнеров используется своя форма:

```bash
efs export odt result.json perechen.odt --format container
```

## Обновление перечня при выходе новой версии

Конфиг переживает обновления — в этом его смысл. Порядок такой:

```bash
efs scan                                     # новый SBOM
efs config init bom.json                     # добавит новые компоненты, сохранит решения
efs config status                            # посмотреть, что появилось незаполненного
efs config find-vcs                          # найти ссылки для новых компонентов
efs postprocess bom.json result.json --app-name ... --app-version ...
efs check result.json
```

Заполнять заново придётся только то, что появилось впервые.

Если нужно перенести метаинформацию из перечня прошлой версии, есть отдельный режим:

```bash
efs update new.json updated.json --update old-perechen.json
```

## Проверка в CI

`efs check` возвращает осмысленный код, поэтому годится для автоматической проверки:

```yaml
- run: efs scan
- run: efs postprocess bom.json result.json --app-name "$PRODUCT" --app-version "$VERSION" --manufacturer "$ORG"
- run: efs check result.json
```

Сборка упадёт, если перечень перестал соответствовать схеме (код `1`) или в нём появились незаполненные компоненты (код `3`). Это ловит ситуацию, когда в продукт добавили зависимость, а перечень не обновили.
